# Performance Enforcement

**Best used when:** the performance rules are agreed, written down, and still not followed — by people, by an AI coding tool, or by both.
**Read before:** adding a hook, writing a `CLAUDE.md`/`AGENTS.md` performance section, or turning on a CI gate.
**See also:** [../performance-from-zero.md](../performance-from-zero.md) · [claude-code.md](./claude-code.md) · [codex.md](./codex.md) · [gemini-cli.md](./gemini-cli.md) · [copilot.md](./copilot.md) · [cursor-cline-aider.md](./cursor-cline-aider.md) · [hooks/](./hooks/)

The guides in `guides/performance/` recommend. This directory enforces. Nothing here explains why a rule exists — every rule links back to the guide that argues for it.

The reason the split matters, in one scar: `repository.findAll().stream().filter(...)` showed up, written by an AI assistant, in two unrelated projects of ours within the same quarter. Both worked in dev with 200 rows. One of them was a table that grows by thousands of rows a day. The rule against it was in the guidelines both times. Guidelines are read, not obeyed.

---

## 1. The three layers

| Layer | What | Runs where | Catches | Bypassed by |
|---|---|---|---|---|
| 1. Instructions | Rules the agent reads before writing code: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.cursor/rules/`, `.clinerules/`, `CONVENTIONS.md` | In the model's context | Most of F1-F8 before the code exists | A long context, a failing build, a human who never read it |
| 2. Hooks | Scripts the tool runs around edits (`PostToolUse` / `AfterTool` / `postToolUse` / `afterFileEdit`) or git `pre-commit` | The developer machine | Anti-pattern shapes in the diff, seconds after they are typed | `--no-verify`, a clone that never installed them, a different tool |
| 3. CI required check | Lighthouse CI assertions, k6 thresholds, the checklist over the PR diff | CI | Everything that survived layers 1 and 2 | Repo admins — so disable admin bypass |

Run all three. Layer 1 catches the honest mistake, layer 2 catches it in seconds instead of a week, layer 3 is the only one that does not care which tool, which machine or which human produced the change.

## 2. What to enforce (the minimum set)

Ten rules. Nothing here is a taste question, and none of it needs a measurement first — these are the structural-hygiene items from [../performance-from-zero.md](../performance-from-zero.md), not optimizations.

| Rule | Layers | Artifact |
|---|---|---|
| Every list endpoint and query is paginated (`page` + `size`, max size 100) | 1, 2, 3 | instruction block · `hooks/perf-review-checklist.sh` [F2] · CI checklist job |
| No DB or HTTP call inside a loop — batch or join | 1, 2 | instruction block · checklist [F1] (heuristic) |
| A column used in `WHERE`/`JOIN`/`ORDER BY` gets an index in the same migration; every FK is indexed | 1, 3 (review) | instruction block · PR template line · `EXPLAIN (ANALYZE, BUFFERS)` in the PR |
| Explicit timeouts on every outbound call | 1, 2 | instruction block · code review (the checklist cannot see this) |
| TTL on every cache key | 1, 2 | instruction block · code review |
| Lazy lists: `ListView.builder`, virtualized web lists | 1, 2 | instruction block · checklist [F3] |
| Lighthouse budget: performance >= 0.9, LCP <= 2500 ms, CLS <= 0.1, first-route JS <= 200 KB | 3 | `hooks/lighthouserc.json` |
| Load-test threshold: p95 < 300 ms read, error rate < 1% | 3 | `hooks/k6-smoke.js` |
| Frame budget < 16 ms at 60 Hz | 1, integration test | instruction block · `integration_test` timeline assertion |
| App size delta < +500 KB per PR unless justified | 3 | `flutter build --analyze-size` step, reviewer |
| No unmeasured claims — a latency number carries the command that produced it | 1 | instruction block · code-review instruction |

The last one has its own scar. A delivery report generated by an AI agent on one of our projects listed "< 100 ms response SLA (< 50 ms typical)" as a shipped feature. Four lines below, under "next steps", it listed "load testing (verify SLAs)". The number was a hope, not a measurement.

Enforcement does not care which model wrote the code. A weaker model needs more of it, not less.

## 4. The canonical instruction block

Written once here. Every per-tool file in this directory embeds the same block, verbatim, in the file that tool reads. Replace nothing except the guide paths if your repo puts them elsewhere.

```markdown
## Performance (non-negotiable)

Two categories. Hygiene is required always and needs no measurement.
Optimization happens only after a measurement names the hotspot.

Structural hygiene — apply without being asked:
1. Every list endpoint and every list query is paginated: `page` + `size`, size clamped
   to a maximum of 100. No `findAll()`, no `SELECT *`, no `.find({})` without a bound.
2. No DB or HTTP call inside a loop (`for`, `forEach`, `.map`, one `useEffect` per row).
   Batch it, join it, or fetch once before the loop.
3. Any column used in `WHERE`, `JOIN` or `ORDER BY` gets an index in the same migration
   as the query that needs it. Every foreign key gets a non-unique index.
4. Every outbound call (HTTP client, DB, queue) sets an explicit connect and read timeout.
5. Every cache key has a TTL. No TTL, no cache.
6. Long lists are lazy: `ListView.builder` in Flutter, a virtualized list on the web,
   a page or keyset query on the server. Never build every row up front.

Optimization — only when I ask, or after a measurement:
7. Do NOT add caching, `@Cacheable`, `React.memo`, `useMemo`, async execution or a thread
   pool unless I ask for it or a profile you ran shows that hotspot.
8. Never claim a latency, a throughput or a complexity you did not measure. Say
   "unmeasured", or paste the command you ran and its output.

Before you call a change done, show me the SQL generated for the main path (or the bundle
size, or the frame time) and the exact command you ran to get it.
```

Two things make this block work, and both come from prompt craft, not from performance: it states **negative constraints** ("do NOT add caching") and it states **success criteria** ("show me the SQL and the command"). A rule with no verifiable output is a suggestion.

## 5. The provider-agnostic recipe

Five steps, in order. Each one works without the next.

**(a) One instruction file.** Put the block above in `AGENTS.md` at the repo root. Codex, Cursor, Copilot and Cline read `AGENTS.md` already; Claude Code and Gemini CLI need one pointer line each ([claude-code.md](./claude-code.md), [gemini-cli.md](./gemini-cli.md)). Keep the whole file short — Codex caps the combined `AGENTS.md` at 32 KiB by default, and every model reads the top of a long file more carefully than the bottom.

**(b) Hooks.** Install `hooks/perf-review-checklist.sh` into `scripts/`, then wire `hooks/perf-post-edit-hook.sh` into the tool that has hooks (the hook finds the checklist next to itself or in `scripts/`). For a tool with no hooks — Cline, aider, Copilot in the editor — use git instead:

```bash
# .git/hooks/pre-commit  (chmod +x; ship the source under scripts/git-hooks/ so it is reviewable)
#!/usr/bin/env bash
exec scripts/perf-review-checklist.sh --staged
```

Keep it report-only (`exit 0`) for the first week and read what it finds. Turn on `PERF_HOOK_BLOCK=1` once the noise is gone; a hook that cries wolf on day one is uninstalled on day two. The `pre-commit` framework's YAML shape for this is `[unverified — check your tool's docs]`.

**(c) CI.** Copy `hooks/github-actions-perf.yml` to `.github/workflows/perf.yml`, `hooks/lighthouserc.json` to the repo root, `hooks/k6-smoke.js` to `perf/`. Mark the three jobs as required checks. Point k6 at staging and never at production: in one of our projects a Playwright run pointed at production sent about 10 real notifications to real users — the same mistake with a load generator is that story with three more zeros.

**(d) PR template.** One line in `.github/pull_request_template.md`:

```markdown
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` output attached for every new or changed query; every FK indexed;
      any latency number in this PR carries the command that produced it.
```

The rule it mirrors is an old one from our review checklist: any code change must have a corresponding test change — if there is none, the tests were wrong. The performance twin is: any new query must have an `EXPLAIN`.

**(e) Review instruction.** Put the review question into whatever reads your diffs (Copilot code review, a Claude review command, a human checklist): *"Can this change hurt performance? A query inside a loop, a load without pagination, objects piling up in memory."* That single question is the seed of this whole directory.

## 6. What the checklist catches, and what it cannot

`hooks/perf-review-checklist.sh` is a grep with opinions. It matches shapes in text; it knows nothing about your schema, your data volume or your render tree.

| Failure mode | Detection | Honest verdict |
|---|---|---|
| F2 unpaged read (`findAll(`, `SELECT *`, `.objects.all()`) | regex on the line | Reliable. This is what it is for |
| F3 unbounded in-memory list (`.findAll().stream()`, `ListView(children: …map())`) | regex + a 3-line window | Reliable for the two canonical shapes; a variable indirection defeats it |
| F1 call inside a loop | `for`/`forEach`/`map` with a repository or `await …find\|get\|fetch\|query` within 3 lines | Heuristic. Catches the shape an AI writes by default; misses anything split across a helper method |
| F4 sync I/O on the hot path (`readFileSync`, `execSync`) | regex, `.ts`/`.js` under `src/` | Partial. **A `RestTemplate`/`WebClient`/`fetch` with no timeout is NOT detectable** — an absent argument has no text to match |
| F5 missing index | none | Needs `EXPLAIN (ANALYZE, BUFFERS)` and the migration. Layer 1 + PR template only |
| F6 premature optimization | none | Needs a human asking "what did you measure?" |
| F7 unmeasured claims | none | Layer 1 and code review |
| F8 fetching the world to render a summary | none | Needs to read the query's intent |
| Render waste, re-render storms, jank | none | Needs the React Profiler or the Flutter frame chart |

So: layer 2 buys you the four cheapest failure modes in seconds. It does not buy you a performance practice.

## 7. The budget file

Layer 3 needs numbers, and numbers need one home. Put `perf-budgets.md` at the repo root (or a section with the same table in `AGENTS.md`) and fill in your own values:

| Signal | Budget | Where measured | Gate |
|---|---|---|---|
| API p95 latency (read) | < 300 ms | k6 against staging | `k6-smoke.js` threshold |
| API p95 latency (write) | < 500 ms | k6 against staging | `k6-smoke.js` threshold |
| Error rate under load | < 1% | k6 | `http_req_failed: ['rate<0.01']` |
| LCP / INP / CLS (p75) | <= 2.5 s / <= 200 ms / <= 0.1 | Lighthouse CI + field RUM | `lighthouserc.json` assertions |
| JS on the first route | < 200 KB gzip | Lighthouse `resource-summary:script:size` | `lighthouserc.json` (bytes: 204800) |
| Frame time | < 16 ms at 60 Hz, < 8 ms at 120 Hz | profile-mode device, `integration_test` timeline | manual + integration test |
| App size delta per PR | < +500 KB unless justified | `flutter build --analyze-size` | reviewer |

Web thresholds are from https://web.dev/articles/vitals and https://docs.flutter.dev/perf/best-practices. The API numbers are a starting point — tune them to your product and then defend them.

**The numbers live in two places.** `k6-smoke.js` and `lighthouserc.json` carry hand-copied duplicates (JSON has no comments and k6 does not read your Markdown). There is no sync mechanism. A reviewer keeps them equal, and changing a budget means changing all three in the same PR.
